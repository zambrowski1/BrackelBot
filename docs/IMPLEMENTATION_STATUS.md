# BrackelBot 0.4: реализованное и ограничения

## Компоненты

| Уровень | Модули | Реализовано |
|---|---|---|
| Данные | api_football_client, player_registry, club_registry, state_store | Официальные GET, квоты, кэш, пагинация, постоянные ID, база сезона/карьеры |
| Обработка | statistics_engine, wikitext_parser, statistics_mapper, change_planner, change_validator | Сезонная дельта, точные строки, атомарные группы, diff, целостность, арифметика |
| Выполнение | GUI, старый CLI, server_cli, scheduler, publisher | Ручные JSON, ежедневный headless цикл, очереди, публикация, проверка ревизий |
| Контроль | operator_review, publication_policy, audit_logger | Просмотр и индивидуальные решения, свежесть, разрешения задач, аварийная блокировка |

Локальные этапы 2–3 сохранены. Новые сезоны, клубы, сборные и сложные переходы
можно выполнять через ранее реализованные ручные JSON в поддерживаемой структуре.
В Automatic сейчас формируются статистические операции текущего периода и
существующего сезона; остальные случаи попадают оператору. Разрешение категории
в policy само по себе не создаёт для неё новый автоматический алгоритм.

## Границы автономности

1. Публикация mainspace возможна технически, но заблокирована по умолчанию.
   Для неё нужны реальные одобрение сообщества и включение оператором.
2. Связи Player ID → QID → статья и API Team ID → QID первоначально подтверждает
   оператор. Автоматический поиск предлагает кандидатов, а не утверждает совпадения.
3. Карьерная база требует проверенного сезонного значения на дату базы. Полная
   историческая статистика всех лиг самостоятельно не собирается.
4. API league=78 покрывает чемпионат. Кубки, еврокубки и сборные не выводятся из
   него. Новые категории и неизвестные значения не превращаются в нули.
5. Native wikitable, неизвестные rowspan/colspan и новые виды шаблонов не
   перестраиваются. Безопасный отказ — обязательная часть поведения.
6. Время получения API не равно подтверждённой дате последнего матча.
   Автоматическая замена даты в карточке пока не производится.
7. Сложные трансферы, аренда и резерв — первоначально ручные операции.
   Автоматический выход из мониторинга требует полного состава и подтверждения
   подходящим трансфером; история не удаляется.
8. Серверные копии сохраняются в ToolsDB. Восстановление целым текстом допускается
   только для testbot, с новым diff и ревизией.
9. Регламент расписания предоставлен, но задание на Toolforge не создавалось.

## Что проверено фактически

Сводка запусков — `verification-server.txt` в корне проекта. Там разделены
обычная установка с Qt, серверная без Qt и проверка сборки. Ответы API-Football
и публикация MediaWiki в автоматических тестах имитируются. Вымышленные данные
из tests/server_helpers.py никогда не отправлялись на Википедию.

Структура API сверена с официальными примерами и валидируется во время каждого
запроса. Документация-v3 закрылась проверкой Cloudflare при чтении из среды;
использованы также [официальный пример всех игроков лиги](https://www.api-football.com/news/post/how-to-get-all-teams-and-players-from-a-league-id)
и [официальное актуальное руководство](https://www.api-football.com/news/post/how-to-get-started-with-api-football-the-complete-beginners-guide).
Поле games.appearences читается отдельно от lineups, null сохраняется неизвестным.

## Что ещё нужно проверить с оператором

- Ваш тариф и доступность сезона 2026 через CHECK_API.bat или check-api.
- Живые ответы всех endpoints, фактические квоты и расход полной лиги.
- Точность исходных карьерных баз и сопоставлений всех отслеживаемых игроков.
- BotPasswords, настоящий тестовый edit и восстановление testbot.
- Создание Tool Account, Python-контейнер, Envvars, ToolsDB и расписание.
- Конкуренцию заданий и аварийную блокировку на настоящем сервере.
- Одобрение задачи русской Википедией и её конкретный разрешённый объём.

Ни реальный Toolforge, ни настоящая база MariaDB в этом сеансе не доступны.
Windows-тест SQLite не доказывает работоспособность ToolsDB. Не выполнялись
массовые правки, создание аккаунтов или подача заявки на флаг бота.
