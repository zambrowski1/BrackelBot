# Работа оператора BrackelBot 0.4

GUI и прежние JSON сохранены. Сервер использует те же parser, planner,
validator и publisher. Новый CLI — `python -m wiki_stats.server_cli` или
установленная команда `brackelbot`. Прежний `wiki-stats` остаётся Dry Run.

## Начать на Windows до создания Toolforge

Распакуйте архив исходников. Для проверки вашего API дважды щёлкните
`CHECK_API.bat`: при первом запуске нужен Python 3.12+ и интернет. Ключ вводится
скрыто в консоли, не сохраняется в исходники или SQLite. Будут выполнены только
`/status` и `/leagues?id=78&season=2026`. Результат покажет тариф, лимит и покрытие.
Получение полного списка и расписание выполняются отдельно.

Для CLI откройте PowerShell в папке исходников:

```powershell
py -3 -m venv .venv-server
.\.venv-server\Scripts\python.exe -m pip install ".[server,test]"
$brackelKey = Read-Host "API-Football key" -AsSecureString
$env:API_FOOTBALL_KEY = [System.Net.NetworkCredential]::new("", $brackelKey).Password
.\.venv-server\Scripts\python.exe -m wiki_stats.server_cli --state local.sqlite3 init-db
.\.venv-server\Scripts\python.exe -m wiki_stats.server_cli --state local.sqlite3 check-api
.\.venv-server\Scripts\python.exe -m wiki_stats.server_cli --state local.sqlite3 run --dry-run
Remove-Item Env:API_FOOTBALL_KEY
```

Последняя команда удаляет переменную из текущего PowerShell. В обычном GUI
API-ключ не требуется: он по-прежнему работает с ручным JSON.

## Справочники и исходная база

Состав клубов берётся из `/teams`, а не из статического списка 18 команд.
Локальные `clubs.json` — каталог идентичностей, включая исторические клубы.
`/players` сезонные записи не являются текущим составом; для текущих связей
дополнительно читается `/players/squads`. Это поведение соответствует
[официальному описанию API](https://www.api-football.com/news/post/how-to-get-started-with-api-football-the-complete-beginners-guide).

После первого Dry Run:

```bash
python -m wiki_stats.server_cli review-list
python -m wiki_stats.server_cli export players players.json
python -m wiki_stats.server_cli export clubs clubs.json
```

Пример последующих команд (подставьте реальные ID, QID и имена; символы в
угловых скобках обозначают значения, а не буквальный текст команды):

```text
python -m wiki_stats.server_cli club-confirm <TEAM_ID> --qid <CLUB_QID> --title "Русская статья клуба" --confirm
python -m wiki_stats.server_cli player-confirm <PLAYER_ID> --qid <PLAYER_QID> --title "Русская статья игрока" --wiki-name "Точное поле имя карточки" --confirm
python -m wiki_stats.server_cli anchor-confirm <PLAYER_ID> verified-anchor.json --confirm
```

На Toolforge запускайте эти команды через `toolforge/operator.sh` внутри
одноразового задания выбранного Python-образа. Например, очередь:

```bash
toolforge jobs run bb-review --image python3.13 --command './brackelbot/toolforge/operator.sh review-list' --wait
```

Player-confirm берёт игрока по API ID из полного сбора сезона, проверяет точную
дату рождения, QID человека, русскую sitelink и обратный pageprops QID. Имя
используется лишь для поиска кандидатов (`run --discover-candidates`), связи
автоматически по нему не создаются. Даже единственного кандидата оператор
подтверждает. Отсутствующая русская статья даёт no_ru_article; создание статей
отсутствует. Слияние различных API ID и замена существующих связей запрещены.

Файл базы устроен как `examples/server/anchor.TEST-ONLY.json`. Обязательны:
API ID клуба, сезон, точный период и викитекст строки; карьерная пара; сезонная
пара **на ту же дату**, дата и подтверждающая ссылка. Числа примера вымышленные.
Anchor-confirm проверяет текущую карьерную строку, клуб и исходные числа.
Подтверждение правильности исходного сезонного показателя — ответственность
оператора: оно не выводится автоматически из карьерной суммы.

Например: база 54 (4), сезон на дату базы 8 (1), сейчас API 10 (2).
Новый карьерный итог: 56 (5). При повторе он не растёт ещё раз: база не меняется
после публикации. База привязана к клубу, сезону и отдельному периоду. Трансфер
после неё, возврат, закрытый исторический период, уменьшение чисел или null
потребуют ручной проверки. Для нового сезона нужна новая подтверждённая база.

## Режимы и публикация

| Команда | Поведение |
|---|---|
| run --dry-run | Сбор, diff, отчёты и очередь; никогда не публикует |
| run --manual | То же, для последующего индивидуального утверждения |
| run --test | Подготовка; публикация отдельной командой только testbot |
| run --automatic | После всех проверок публикует разрешённые API-планы; по умолчанию заблокирован |

`--test` не переносит реальные статьи молча на тестовую страницу. Для testbot
используйте явные тестовые JSON из examples/stage23 или пакет для нужного игрока.
Для установки полного стенда и восстановления подходит [SAFE_TESTING.md](SAFE_TESTING.md).

Пример серверного теста с явным пакетом:

```text
python -m wiki_stats.server_cli import-json examples/stage23/07-combined-atomic.json
python -m wiki_stats.server_cli review-list --plans
python -m wiki_stats.server_cli review-show <HASH>
python -m wiki_stats.server_cli review-approve <HASH> <OPERATION_ID> --confirm
```

Повторите review-approve для **каждой** изменяемой операции группы.
HASH берётся из import-json или review-list. Перед утверждением обязателен
review-show. Только после проверки всех diff и вашего разрешения:

```text
python -m wiki_stats.server_cli kill-switch off --confirm
python -m wiki_stats.server_cli publish <HASH> --test
```

Перед этим BRACKELBOT_PUBLICATION должна быть равна 1, а WIKI_BOT_USERNAME и
WIKI_BOT_PASSWORD — заданы через Envvars. Даже с ними Test не пишет другие
страницы. Live API-планы в основном пространстве требуют отдельного одобрения.
Не используйте эти команды публикации до установки нужного стенда и разрешения
оператора. Разработчик их на реальной Википедии не выполнял.

## Ручные операции в основном пространстве после одобрения

Загрузите живой ручной пакет с правильным subject_scope, затем выполните
`attest-manual <HASH> --api-id <PLAYER_ID> --season 2026 --confirm`.
Это явное подтверждение оператором источников и связи статьи. После него всё
ещё нужны просмотр, отдельные review-approve, точный список разрешённых задач
и `publish <HASH> --manual`. Ручная аттестация никогда не допускается в Automatic.
Планы из `--fixtures` не публикуются: потребуется новая живая проверка.

## Что формируется автоматически

- Подтверждённая карьерная статистика текущего периода по базе и сезонной дельте.
- Существующая строка сезона формата 2026/27 в КлСтат, только колонка Чемпионат.
- Однозначные итоги КлСтат, когда все остальные категории содержат известные числа.
- Связанная атомарная группа карточки и таблицы; повторная обработка без новой правки.

Новая строка сезона не заполняется нулями: если кубковые категории неизвестны,
создаётся очередь ручного дополнения. Карточка и существующие поддерживаемые
строки остаются доступными. Трансферы записываются в очередь с датой и клубами;
неизвестный дебют, начало периода, аренда или возврат не угадываются.
Клубные переходы, новые сборные, сезоны и структура редактируются существующими
ручными JSON. Национальная статистика не выводится из гражданства или league=78.

Дата получения API записана в отчёт и источники как дата получения. Она не
превращается автоматически в дату последнего сыгранного матча или параметр
обновления данных о клубе. Для этого требуется подтверждённый охват и ручной
update_date. Native wikitable с произвольными rowspan/colspan и неизвестные
вложенные шаблоны сохраняют безопасный unsupported_structure.

## Лимиты, очередь и восстановление

Все страницы игроков должны загрузиться до обработки. Пустая или оборванная
выборка не считается составом. Полученные страницы кэшируются 6 часов;
повторный запуск использует их и продолжает незавершённый сбор. Изменившееся
количество страниц блокирует сбор. Составы и трансферы тоже кэшируются;
перед записью персональные данные читаются заново без кэша.

Daily/minute remaining берутся из реальных заголовков; квота аккаунта также
проверяется через status. Когда лимит кончился, цикл останавливается с отчётом,
без автоматического повторения POST. Кэш не скрывает неполноту выборки.
На дешёвом тарифе лимита может не хватить на всю лигу, составы, трансферы и
повторную проверку; фактический расход виден в requests отчёта. Подписку и сезон
2026 нужно проверить вашим ключом, наличие аккаунта само по себе недостаточно.

Отсутствие игрока в списке статистики не удаляет его из справочника. Выход из
мониторинга фиксируется лишь при полном сборе составов и подходящем свежем
трансфере за пределы сезонных клубов. История и база сохраняются; оформление
карьеры отправляется оператору. Неподтверждённое отсутствие остаётся в review.

`export runs`, `export review`, `export edits` и `export audit` сохраняют JSON.
Каждый цикл создаёт также TXT и JSON отчёты. `backup-export <KEY> file.json`
выгружает конкретную исходную копию из ToolsDB. `restore-test file.json`
создаёт diff восстановления testbot; для него снова нужны просмотр, утверждение
и publish --test. Восстановление основных статей целым текстом не реализовано.

Если ответ POST потерян, publication_unknown аннулирует план. Проверьте историю
и получите свежую ревизию; повторять запрос автоматически нельзя. При конфликте
ревизии старые подтверждения снимаются. Критическая ошибка разбора блокирует
публикацию всего цикла. Аварийная блокировка: kill-switch on.
